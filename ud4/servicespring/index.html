    🧩 Capa Service en Spring: @Service

    🎯 Objetivo: entender qué es un Service, por qué existe y cómo se usa junto a los Repositories para construir una aplicación limpia, mantenible y fácil de testear.

    🧠 1) ¿Qué es un @Service?

    ✅ @Service es una anotación de Spring para marcar una clase como componente de la capa de negocio.

    • 🧱 Es un Bean: Spring lo crea y lo gestiona (IoC).
    • 🔌 Se inyecta donde haga falta (DI).
    • 🧭 Contiene lógica de negocio: reglas, validaciones, orquestación de repositorios, llamadas a otros servicios, etc.

    📌 Piensa en el Service como el sitio donde decides “qué se puede hacer y cómo”, no “cómo se guarda”.

    🧱 2) ¿Por qué existe la capa Service? (y por qué NO meterlo todo en el Controller)

    ✅ Service te da:

    • 🧠 Reglas de negocio en un sitio (no duplicadas en controllers).
    • 🧪 Testabilidad (puedes probar lógica sin HTTP).
    • 🔁 Reutilización (varios controllers pueden usar el mismo service).
    • 🔒 Transacciones (muy típico que el @Transactional viva aquí).
    • 🧹 Orden (separación de responsabilidades).

    🚫 Evita esto:

    • Controllers con 200 líneas.
    • Lógica repetida en varios endpoints.
    • Repositorios “con lógica rara” mezclando decisiones de negocio.

    🧩 3) Arquitectura típica

    • 🗃️ Repository → Acceso a datos (CRUD, consultas)
    • 🧠 Service → Reglas y casos de uso (negocio)
    • 🌐 RestController → HTTP (request/response)

    📌 Regla práctica:

    🌐 El Controller traduce HTTP → Java y Java → HTTP
    🧠 El Service ejecuta el caso de uso
    🗃️ El Repository habla con la BD

    🧷 4) Ejemplo mínimo: Repository + Service

    🗃️ UserRepository

    public interface UserRepository extends JpaRepository<User, Long> {
  Optional<User> findByEmailIgnoreCase(String email);
  boolean existsByEmailIgnoreCase(String email);
}

    🧠 UserService

    import org.springframework.stereotype.Service;

@Service
public class UserService {

  private final UserRepository userRepository;

  // ✅ Inyección por constructor (recomendada)
  public UserService(UserRepository userRepository) {
    this.userRepository = userRepository;
  }

  @Transactional
  public User register(User user) {
    if (user == null) throw new IllegalArgumentException("user es obligatorio");
    if (user.getEmail() == null || user.getEmail().isBlank())
        throw new IllegalArgumentException("email es obligatorio");

    // 🧠 Regla de negocio: email único
    if (userRepository.existsByEmailIgnoreCase(user.getEmail())) {
      throw new ConflictException("Ya existe un usuario con ese email");
    }
    // 🗃️ Persistencia
    return userRepository.save(user);
  }

  @Transactional(readOnly = true) //esto es opcional
  public User findByEmail(String email) {
    if (email == null || email.isBlank()) {
        throw new BadRequestException("email es obligatorio");
    }
    return userRepository.findByEmailIgnoreCase(email)
        .orElseThrow(() -> new NotFoundException("No existe el usuario"));
  }
}

    ✅ Observa: - El repo solo sabe guardar/buscar. - El service decide si se puede y qué pasa si no.

    🔄 5) @Transactional: lo normal es ponerlo en Service

    @Transactional significa: “este método se ejecuta dentro de una transacción de base de datos”.

    Una transacción es un bloque de trabajo con estas reglas (ACID):

    • ✅ Todo o nada: si algo falla, se deshace todo (rollback).
    • ✅ Consistencia: la BD no queda a medias.
    • ✅ Aislamiento: otros no ven cambios “a medio hacer” (según nivel).
    • ✅ Durabilidad: si confirma (commit), queda guardado.

    ❓ Cuándo hay que poner @Transactional

    1. Cuando un caso de uso hace varias operaciones (varios save, cambios en varias entidades, etc.), lo típico es controlar la transacción en el Service poniendo @Transactional.
    @Transactional
public Match createMatch(Long playerId, Long cabinetId) {
  Player p = playerRepo.findById(playerId).orElseThrow();
  Cabinet c = cabinetRepo.findById(cabinetId).orElseThrow();

  c.setStatus(Status.BUSY);          // update
  Match m = new Match(p, c);
  matchRepo.save(m);                  // insert

  return m;                           // si falla algo → rollback de todo
}

    Sin transacción podrías quedarte con:

    match guardado, cabinet no actualizado (o al revés) → inconsistencia

    1. Cuando modificas entidades “gestionadas” sin llamar a save explícitamente. Con JPA/Hibernate, si dentro de una transacción cargas una entidad y le cambias campos, Hibernate hace dirty checking y sincroniza al hacer commit.
    @Transactional
public void deactivateCard(Long cardId) {
  RfidCard card = cardRepo.findById(cardId).orElseThrow();
  card.setActive(false); // no llamas a save, pero se persiste al commit
}

    Si no hay transacción, ese cambio puede no persistirse como esperas (depende de cómo esté configurado y de cuándo se hace flush).

    1. Para evitar problemas con LAZY loading. Si cargas una entidad con relaciones LAZY y luego accedes a ellas, necesitas que la sesión/tx siga activa:
    @Transactional(readOnly = true)
public User getUserWithSpaces(Long id) {
  User u = userRepo.findById(id).orElseThrow();
  u.getSpaces().size(); // fuerza carga LAZY dentro de la tx
  return u;
}

    Ejemplo correcto usando excepciones:

    import org.springframework.transaction.annotation.Transactional;

@Service
public class MatchService {

  private final MatchRepository matchRepository;
  private final PlayerRepository playerRepository;
  private final CabinetRepository cabinetRepository;

  public MatchService(MatchRepository matchRepository,
                      PlayerRepository playerRepository,
                      CabinetRepository cabinetRepository) {
    this.matchRepository = matchRepository;
    this.playerRepository = playerRepository;
    this.cabinetRepository = cabinetRepository;
  }

  @Transactional
  public Match createMatch(Long playerId, Long cabinetId) {
    Player player = playerRepository.findById(playerId)
        .orElseThrow(() -> new ResourceNotFoundException("Player no existe"));
    Cabinet cabinet = cabinetRepository.findById(cabinetId)
        .orElseThrow(() -> new ResourceNotFoundException("Cabinet no existe"));

    Match match = new Match();
    match.setPlayer(player);
    match.setCabinet(cabinet);

    return matchRepository.save(match);
  }
}

    📌 Idea clave:
    - 1 caso de uso → 1 transacción (normalmente).
    - El Controller no debería “saber” de transacciones.

    🧰 6) Buenas prácticas típicas en Service

    ✅ Inyección por constructor

    • 🧱 Facilita tests
    • 🧼 Evita @Autowired “por todas partes”

    ✅ Services pequeños y con nombre de caso de uso

    • registerUser, issueCard, assignTag, createMatch
    • Mejor que “todo en un UserManagerMegaService”

    ✅ Validaciones de negocio aquí

    • Unicidades, estados permitidos, límites, reglas

    ✅ No devolver Optional hacia arriba “porque sí”

    • Lo normal es resolverlo en service y lanzar excepción o devolver un DTO. No devolver un Optional al Controller.

    🧨 7) Errores comunes

    • ❌ Service que solo hace return repository.save(x); en 20 métodos sin reglas (a veces no es necesario un service tan grande).
    • ❌ Controller llamando a 3 repositorios directamente.
    • ❌ Lógica de negocio en @Entity mezclada con persistencia (ojo, el dominio puede tener métodos, pero no debería depender de Spring/JPA).
    • ❌ @Transactional puesto en cualquier sitio sin sentido.

    ✅ Checklist antes de pasar a @RestController

    Antes de crear endpoints, asegúrate de que:
    - 🧠 Los casos de uso están en Services.
    - 🗃️ Los repos están “finos” (CRUD y queries).
    - 🔄 Las transacciones están donde toca.
    - 🧪 Puedes probar servicios sin HTTP.
